# 计划详情页改版设计（间距 · 打卡表 · 任务与提交 · 逾期策略）

**日期**：2026-04-14  
**范围**：`apps/web-user` 计划详情页（`PlanDetailPage.vue`）及相关 API 行为说明  
**状态**：待产品确认后进入实现（建议再执行 `writing-plans` 拆 Story）

---

## 1. 背景与目标

详情页已具备：面包屑、状态/类型、Markdown 正文、**打卡计划**（按 slot 卡片 + 编辑/恢复弹窗）、**任务清单**（表格 + 跳转任务提交页）。本次围绕四个问题收敛交互与规则，避免「左右留白过大、信息分散、逾期规则不清」。

---

## 2. 现状摘要（代码事实）

| 区域 | 实现要点 |
|------|-----------|
| 主内容宽度 | 外层 `mx-auto w-full max-w-5xl` + `p-4 sm:p-6 lg:p-8`，在大屏上内容区居中、两侧留白随视口变宽而增大 |
| 打卡计划 | `checkinSchedule.slots` 以 **2 列网格卡片**展示，每卡含 `slotKey`、正文、`编辑`/`恢复` |
| 任务清单 | 独立 `<section>` 表格，`taskRows` 来自 `executionSnapshot.stages[].tasks`，操作链到 `/tasks/:taskId/submit` |
| 逾期与编辑 | `updatePlanScheduleSlot`（`plan.service.ts`）**未**校验计划 `deadline`；`POST /tasks/:taskId/submissions` **未**校验计划截止，且注释说明任务归属校验较弱 |

---

## 3. 议题与方案

### 3.1 详情页与两侧间隔是否过大

**判断**：在宽屏下 `max-w-5xl`（约 64rem）+ 较大水平 `padding` 会让「有效阅读宽度」相对变窄、两侧灰带偏宽，属主观体验问题，但可量化调整。

**可选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A（推荐）** | `max-w-5xl` → `max-w-6xl` 或 `max-w-7xl`，并略减 `lg:p-8` → `lg:p-6` | 同样居中但内容更宽，表格/打卡表更易扫读 | 极宽屏上行宽过长可能影响长文阅读 |
| **B** | 保持 `max-w-5xl`，仅减小水平 padding（`lg:px-4`） | 改动小 | 两侧仍明显留白 |
| **C** | 打卡/任务区在 `xl`  breakpoint **局部全宽**（负 margin 或独立外层），Hero 仍限宽 | 数据密集区更宽 | 布局复杂度上升，需统一与列表页栅格 |

**推荐**：**A** 为主；若打卡改为宽表（见 3.2），可再评估 **C** 仅对「打卡+（若保留）任务」区域放宽。

---

### 3.2 打卡计划是否改成表格形式

**判断**：slot 数量多时，卡片网格纵向占用大、列对齐弱；**表格**更利于对比日期/周期与操作列。

**可选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A（推荐）** | `md+` 用 `<table>`：列如「时间槽 / 内容摘要 / 状态 / 操作」；`sm` 以下保留卡片或折叠行 | 信息密度与可扫读性更好 | 需处理长正文（摘要+展开 或 tooltip） |
| **B** | 始终表格 + 横向滚动 | 实现简单 | 小屏体验一般 |
| **C** | 保持卡片，仅改为单列列表 | 改动最小 | 未解决「表格化」诉求 |

**推荐**：**A**，内容与 `slotKey` 较长时：内容列显示前 2 行 +「展开」，弹层或行内展开全文。

---

### 3.3 是否去除任务清单，并把「提交完成内容」放进打卡计划

**判断**：产品意图是**单一执行面**：用户按「时间槽」打卡，而不是先在任务表再找提交入口。但当前**数据模型不同**：

- **任务提交**：`POST /tasks/:taskId/submissions`，需 `content` + **至少一张图片 URL**（见 `submission.routes.ts`）。
- **打卡 slot**：仅有 `slotKey`、文本 `content`，与 `task.id` **无显式外键**；`stages/tasks` 与 `schedule.slots` 来自同一生成快照但结构独立。

因此「去掉任务表、提交并入打卡」不是纯前端搬家，必须选定一种**关联或新资源**策略。

**可选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A（推荐·渐进）** | 详情页**隐藏独立任务表区块**；每个 slot 行提供「去提交」：若后端/启发式能映射到**单个任务**则链到现有 `/tasks/:id/submit`；无法映射时显示「请从任务列表提交」或引导到**第一个未完成任务**（需规则文档化） | 复用现有提交 API 与校验 | 映射规则需设计（按阶段顺序、按日期重叠等），可能不完美 |
| **B** | 新增 **`slotKey` 维度提交** API（如 `POST /plans/:id/schedule/slots/:slotKey/submissions`），数据结构与 TaskSubmission 对齐或简化（是否仍强制图片） | 模型与 UI 一致、可去掉任务表 | **后端 + 库表 + 迁移**；与现有任务体系并行或迁移成本高 |
| **C** | 保留任务表但**折叠/次要入口**，打卡区放主按钮「关联到本周任务」 | 风险低 | 未完全满足「去除任务清单」 |

**推荐**：若必须**去掉任务表**：优先定稿 **B** 的长期模型；短期可用 **A** 做 MVP（需产品接受映射近似）。**不建议**在未定义 API 的情况下仅前端删除任务表并把按钮写死到某一 taskId。

**依赖决策（需产品确认）**：

1. 提交是否仍**强制图片**？若打卡场景以文字为主，是否放宽为「图片可选」？
2. slot 与 task 的对应关系：一对一、多对一，还是仅「计划级」一个提交入口？

---

### 3.4 超过完成时间的计划是否还能再提交或编辑

**现状**：后端对 **schedule 编辑**与**任务提交**均未按 `plan.deadline` 拦截 → **技术上始终允许**。

**产品策略选项**：

| 策略 | 行为 | 适用 |
|------|------|------|
| **S1（推荐默认）** | 允许提交与编辑；UI 标注「已逾计划截止日，补记」类文案 | 自律工具、减少挫败感 |
| **S2** | 截止后**禁止**新提交与 schedule 编辑；只读历史 | 强契约场景 |
| **S3** | 禁止**新**提交，但允许编辑 schedule 文案（或相反） | 折中，需说明理由 |
| **S4** | 按 **slot 结束日期** 细粒度禁用（若将来 slot 带日期区间） | 更精细，实现复杂 |

**推荐**：**S1** 为默认产品行为，与当前 API 一致；若选 **S2/S3**，需在 **`updatePlanScheduleSlot`** 与 **`createSubmission`**（及对应 service）增加统一截止时间校验，并返回明确错误码供前端展示。

---

## 4. 推荐组合（供拍板）

1. **布局**：采用 **3.1-A**（略加 max-width、略减大屏 padding），打卡改表后再视情况加 **3.1-C** 局部加宽。  
2. **打卡**：采用 **3.2-A** 响应式表格 + 小屏卡片。  
3. **任务与提交**：优先确认 **3.3** 的 B vs A；在 API 未定前，**不要**删除任务表以免用户无路提交。  
4. **逾期**：默认 **S1**；若需 S2/S3，单列一期「后端校验 + 前端禁用态」Story。

## 6. 建议实施顺序（实现阶段草案）

| 阶段 | 内容 | 风险 |
|------|------|------|
| **Phase 1** | 仅布局与打卡表格 UI（保留任务表） | 低 |
| **Phase 2** | 产品确认 slot↔task 或新 API 后，移除/隐藏任务表并接提交 | 中–高 |
| **Phase 3** | 逾期策略后端 + 前端 | 中（需与 Phase 2 错误处理一致） |
